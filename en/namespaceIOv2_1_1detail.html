The type actually written back to on extraction: an lvalue target keeps its type, an rvalue target is demoted to const.

Note
This layer is what decides "can this be written into". It is what rejects is >> 5 and is >> const_obj: the sread for int takes an int&, which a const int& cannot match. A manipulator produced by a factory such as setw(5) is a prvalue, but its sread does not modify the manipulator object and takes a const reference, so it passes.

◆ crt_locale_is_utf8()

bool IOv2::detail::crt_locale_is_utf8 ( )
inlineconstexprnoexcept

Only the Windows backend needs to tell: on POSIX wchar_t is not UTF-16 and a UTF-8 locale goes through mbrtowc/wcrtomb like any other, so this is always false.

Whether the calling thread's current LC_CTYPE is UTF-8 (code page 65001). Call it under a clocale_user. There mbrtowc silently turns a character outside the BMP into U+FFFD and wcrtomb_s rejects surrogates, so the locale kernel converts UTF-8 to and from UTF-16 itself.

◆ ctype_byte_is_char()

bool IOv2::detail::ctype_byte_is_char ( int ,
clocale_handle  )
constexprnoexcept

Whether byte c is a character of its own in loc, fit for is*_l/to*_l.

Always true on glibc, which does not classify high bytes of a multibyte locale in the first place. macOS classifies a byte as the Unicode code point of the same value, whatever the encoding: under UTF-8 it makes 0x80-0x9F cntrl and 0xE9 a letter, although there they are only parts of multibyte sequences. So on macOS a high byte of a multibyte locale belongs to no class and keeps its case, as on glibc.

Whether c belongs to cls, a mask from ctype_wctype (c belongs if it has any of its bits). The bits of c come from GetStringTypeW(CT_CTYPE1, ...); the file comment says why.

print is decided apart: wctype("print") is _BLANK|_PUNCT|_ALPHA|_DIGIT, and GetStringTypeW gives tab C1_BLANK as well. C makes printing and control characters disjoint (C11 7.4/3), so a blank prints only if it is not a control character, as in the byte-wise ctype_isprint.

◆ ctype_map_case()

wint_t IOv2::detail::ctype_map_case ( wint_t c,
unsigned long flags,
clocale_handle loc )
inlinenoexcept

Case-maps one UTF-16 code unit by loc's LC_CTYPE; flags is LCMAP_UPPERCASE or LCMAP_LOWERCASE.

Not the UCRT's _towupper_l/_towlower_l: below 256 they look the character up in a table built from the locale's code-page bytes, using the code point as a code-page byte, which is wrong under a code-page locale (measured by the probe: U+00FF -> U+009F under 1252, U+00FF -> U+00DF under 1251, U+00DF -> U+00BA under 1253). LCMapStringEx maps by Unicode and is right in every locale; LCMAP_LINGUISTIC_CASING makes it agree with glibc (U+00B5 -> U+039C, U+0131 -> I, U+01C5 -> U+01C4, Turkish i -> U+0130).

The "C" locale has no BCP-47 name and, like the UCRT's and glibc's "C", maps ASCII only. Returns c if the mapping fails or does not give a single code unit.

◆ stdin_io_mutex()

copyable_mutex< std::recursive_mutex > & IOv2::detail::stdin_io_mutex ( )
inline

The object lock the standard input streams share: every stdin_api (cin, wcin) has it as its io_mutex().

They read the same fd 0, so they share a lock, and an operation on one waits for an operation under way on another. It is never destroyed, like cin and wcin themselves (they are not destroyed at exit and may still be used while the program exits). As with the eight standard streams, "one" rests on a single module, or every module built with IOV2_SHARED; see the @note in IOv2/io/objects/objects.h.

◆ tm_stream_format()

template<typename TChar>
std::basic_string< TChar > IOv2::detail::tm_stream_format ( const timeio< TChar > & tio)

The format os << tm and is >> tm share: an expanded c, plus z and (Z) where those are needed.

The locale's c is first run through timeio::expand_format, because a z can sit inside a compound such as r or X where no search would find it; z and Z are then tested separately and whichever is missing is appended.

Each specifier is appended on its own. z restores tm_gmtoff, Z restores tm_zone, and neither stands in for the other: an abbreviation does not determine an offset (CST is US Central −6, China +8 and Cuba −5 at once), and an offset does not give a zone name. So en_US's c already carrying a Z still does not spare it the appended z. An appended Z is parenthesized and an appended z is not, giving ... +0800 (CST); a locale that already has a Z gets nothing appended for it and so stays ... Z z.

It is appended unconditionally, not based on this particular tm – sread holds a time_parse_context and no std::tm to inspect. Only one value-independent format, shared by both sides, keeps whatever can be written readable. Nothing is appended when the platform's std::tm has neither tm_gmtoff nor tm_zone, where appending would only put those characters in the output.

char32_t & cp )
constexprnoexcept

Decode the UTF-8 character at from into a code point (from != from_end required), strictly per RFC 3629: overlong encodings, surrogate code points, values above 0x10FFFF and malformed continuation bytes are rejected. On ok, cp is the code point and from moves past the character; otherwise both are left alone (from stays at the character's start). How the code point becomes internal units is up to each UTF-8 kernel.
