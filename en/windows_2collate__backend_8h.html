Detailed Description

Windows backend of the collate facet: CompareStringEx and LCMapStringEx(LCMAP_SORTKEY), called directly, with the collation rules picked by the locale's LC_COLLATE BCP-47 name.

Not the UCRT's _strcoll_l/_strxfrm_l: the former passes SORT_STRINGSORT to CompareStringEx, the latter calls LCMapStringEx without it, so the order of the keys disagrees with the comparison (measured on real Windows under de-DE: "co-op" is less than "coat", its key greater than "coat"'s). The MSVC STL's collate, which calls NLS itself, disagrees the same way. This backend passes no flag to either: punctuation is ignored at the first level, which agrees with glibc on that example.

A narrow string goes to UTF-16 first, by MultiByteToWideChar in the code page of LC_COLLATE, with MB_ERR_INVALID_CHARS: a byte sequence invalid in that code page is a failure, as it is for the UCRT's _strcoll_l. The key LCMapStringEx produces is a string of bytes: a narrow key is those bytes, a wide key one byte per wchar_t, as in the UCRT's wcsxfrm.

The "C" locale has no BCP-47 name and, as in the UCRT, compares by code unit, its key being the input itself. Wide characters are UTF-16 code units, so under "C" a character outside the BMP sorts before U+E000-U+FFFF.
